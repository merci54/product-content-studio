# Product Content Studio

Невеликий редактор товарних карток для інтернет-магазину. Менеджер у захищеній адмін-панелі редагує опис і SEO-поля товару, зберігає зміни та публікує картку. Відвідувачі бачать каталог опублікованих товарів і сторінку кожного з них.

## Стек

| Що                | Чим                                                    |
| ----------------- | ------------------------------------------------------ |
| Фреймворк         | Next.js 16 (App Router), React 19, TypeScript          |
| Стилі             | Tailwind CSS 4, адаптивна верстка, світла й темна тема |
| База даних        | SQLite + Prisma 7 (драйвер `better-sqlite3`)           |
| Валідація         | Zod 4 — одна схема для форми та сервера                |
| Авторизація       | JWT (`jose`) у httpOnly-cookie, паролі — bcrypt        |
| API               | REST (Route Handlers), клієнт — axios                  |
| Тести             | Vitest (unit), Playwright (e2e + API)                  |
| CI                | GitHub Actions                                         |
| Якість коду       | ESLint, Prettier                                       |
| Пакетний менеджер | npm                                                    |

## Вимоги

- **Node.js 24** — версія зафіксована в `.nvmrc`, достатньо виконати `nvm use`.
- npm.
- Docker, зовнішні сервіси та API-ключі не потрібні.

## Швидкий старт

```bash
nvm use
npm ci
cp .env.example .env
```

У `.env` задайте власний `ADMIN_PASSWORD` і випадковий `JWT_SECRET`. Згенерувати секрет:

```bash
openssl rand -base64 32
```

Створіть базу та заповніть її демонстраційними даними:

```bash
npx prisma migrate deploy
npx prisma db seed
```

Запустіть застосунок:

```bash
npm run dev
```

Застосунок відкриється на http://localhost:3000.

- `npm ci` автоматично виконує `prisma generate` (скрипт `postinstall`), тому окремо генерувати Prisma Client не потрібно.
- Seed створює адміністратора та три товари: два опубліковані й одну чернетку. Seed ідемпотентний, його можна запускати повторно — дублікати не з'являться.

## Вхід в адмін-панель

- Посилання «Адмін-панель» у шапці або адреса http://localhost:3000/login.
- Логін і пароль — значення `ADMIN_EMAIL` і `ADMIN_PASSWORD` з вашого `.env`.
- У базі зберігається лише bcrypt-хеш пароля. Якщо змінили пароль у `.env`, повторно виконайте `npx prisma db seed`.

## Тести

```bash
npm test                      # unit-тести (Vitest)
npx playwright install chromium   # один раз: браузер для e2e (~150 МБ)
npm run test:e2e              # e2e та API-тести (Playwright)
npm run lint                  # ESLint
```

E2E-тести самі піднімають **production-збірку** на порту **3100** з **окремою базою `test.db`** і власними тестовими обліковими даними (`tests/e2e/test-env.ts`). Ваш `.env` і `dev.db` вони не змінюють. Перед кожним запуском `test.db` створюється заново, тому результат не залежить від попередніх запусків. Перший запуск триває близько хвилини через `next build`.

## CI

GitHub Actions (`.github/workflows/ci.yml`) запускається на кожен push у `main` і на кожен pull request. На чистій машині з Ubuntu та Node 24 виконуються:

1. `npm ci` (разом із `prisma generate`);
2. перевірка форматування Prettier;
3. ESLint;
4. unit-тести;
5. e2e та API-тести на production-збірці (`next build` входить у цей крок).

Секрети GitHub не потрібні: e2e-тести використовують власну базу й тестові облікові дані. Якщо тести падають, trace-файли Playwright зберігаються як артефакт запуску на 7 днів.

## API

| Метод | Шлях                       | Доступ        | Що робить                                             |
| ----- | -------------------------- | ------------- | ----------------------------------------------------- |
| GET   | `/api/products`            | публічний     | список опублікованих товарів                          |
| GET   | `/api/products/[slug]`     | публічний     | опублікований товар; для чернетки й неіснуючого — 404 |
| POST  | `/api/auth/login`          | публічний     | вхід, встановлює cookie сесії                         |
| POST  | `/api/auth/logout`         | —             | вихід, видаляє cookie                                 |
| GET   | `/api/admin/products`      | адміністратор | усі товари з назвою та статусом                       |
| GET   | `/api/admin/products/[id]` | адміністратор | товар для редактора                                   |
| PATCH | `/api/admin/products/[id]` | адміністратор | зберегти опис, SEO-заголовок, SEO-опис і статус       |

Коди відповідей: `400` — некоректні дані (з переліком помилок по полях), `401` — немає входу, `404` — товар не знайдено, `500` — помилка сервера.

## Основні технічні рішення

- **SQLite.** База — один файл, без сервера й Docker, тож проєкт запускається однією послідовністю команд. Для продакшену з кількома екземплярами застосунку варто взяти PostgreSQL: змінюються `provider` у схемі Prisma та драйвер-адаптер.
- **JWT у httpOnly-cookie.** Токен підписаний HS256, живе 8 годин. Cookie має прапорці `HttpOnly` (недоступна JavaScript), `SameSite=Lax` (захист від CSRF) і `Secure` у продакшені. Під час перевірки дозволено лише алгоритм HS256 — це захищає від підробки через `alg: none`.
- **Дві лінії захисту адмінки.** `proxy.ts` перенаправляє зі сторінок `/admin` на `/login`. Кожен адмін-ендпоінт і кожна адмін-сторінка додатково самі перевіряють сесію: без входу API повертає `401`.
- **Одна Zod-схема для форми та сервера** (`lib/validation/product.ts`). Ліміти 1000 / 60 / 160 символів, порожні рядки й рядки з самих пробілів відхиляються. `strictObject` відхиляє зайві поля, тож назву та характеристики неможливо змінити навіть прямим запитом до API (захист від mass assignment).
- **Чернетка недоступна публічно.** Сторінка та публічний API шукають лише товари зі статусом `PUBLISHED`. Чернетка й неіснуючий slug дають однакову відповідь `404`, тож зовні не можна дізнатися навіть про існування чернетки.
- **Вміст товару не виконується як код.** Опис виводиться як текст (без `dangerouslySetInnerHTML`), React екранує HTML. Це перевіряє e2e-тест із `<img onerror>` і `<script>` в описі.
- **Cache Components вимкнено.** З ними сторінка чернетки в production-збірці віддавала статус `200` замість `404` (soft 404): заголовки надсилаються до виклику `notFound()`. Усі сторінки й так залежать від свіжих даних бази, тож кешування нічого не дає.
- **`connection()` у запитах каталогу.** Драйвер `better-sqlite3` синхронний, і без `connection()` Next.js виконав би запит під час збірки й закешував каталог. Так зміна статусу одразу видна відвідувачам.
- **Невдале збереження не стирає правки.** Форма редактора зберігає введені значення при будь-якій помилці, блокує поля на час запиту, показує причину помилки й не показує її як успіх. При закритті вкладки з незбереженими змінами браузер просить підтвердження.
- **Server Components для читання даних.** Сторінки читають базу напряму через функції з `lib/products.ts`, без запитів до власного API. REST API — окремий вхід для зовнішніх клієнтів, і обидва шляхи використовують ті самі функції.

## Стратегія тестування

Тести поділені на два рівні.

**Unit-тести (Vitest, `tests/unit`)** — правила безпеки, які є чистими функціями:

- валідація товару: граничні значення (60 приймається, 61 відхиляється, так само для 160 і 1000), порожні поля й поля з пробілів, невідомий статус, спроба передати назву або характеристики;
- перевірка JWT: коректний токен, токен з іншим секретом, змінений, прострочений і непідписаний (`alg: none`);
- розбір id з URL.

Їх вигідно перевіряти швидкими unit-тестами: вони виконуються за мілісекунди й точно показують, яке правило порушено.

**E2E та API-тести (Playwright, `tests/e2e`)** — критичні сценарії через усі шари одразу (браузер → API → Prisma → SQLite) на production-збірці:

- публічна частина: у каталозі лише опубліковані товари; SEO-поля в заголовку та описі сторінки; чернетка недоступна за прямим URL і через публічний API (статус `404`); HTML в описі не виконується;
- адмін-API: без входу всі ендпоінти повертають `401`; невірний пароль і неіснуючий email дають однакову відповідь; сім варіантів некоректних даних отримують `400`, і товар у базі не змінюється; коректні дані зберігаються;
- адмін-панель: редирект без входу; публікація чернетки робить її видимою в каталозі; занадто довгий SEO-заголовок не відправляється на сервер; при обриві мережі правки лишаються у формі, а в базі нічого не змінюється; після виходу адмінка знову недоступна.

**Чого немає і чому.** Окремих тестів React-компонентів (Testing Library) немає: форма редактора вже перевіряється в e2e у справжньому браузері, а повторення тих самих перевірок на рівні компонентів дало б те саме покриття ціною додаткового коду.

## Структура проєкту

```
app/                  сторінки та API (App Router)
  (auth)/login/       сторінка входу
  admin/              список товарів і редактор
  api/                REST API: публічне, auth, admin
  products/[slug]/    сторінка товару
components/           React-компоненти (кожен у своїй папці)
lib/
  db/prisma.ts        підключення до бази
  auth/session.ts     створення, перевірка й видалення JWT-сесії
  api/                клієнт axios для форм
  validation/         Zod-схема товару та ліміти
  utils/              допоміжні функції
  products.ts         запити до товарів
prisma/               схема, міграції, seed
proxy.ts              захист сторінок /admin
tests/unit/           unit-тести (Vitest)
tests/e2e/            e2e та API-тести (Playwright)
```

## Відомі обмеження

- Після виходу токен видаляється лише з браузера. Відкликати його на сервері не можна — він дійсний до завершення строку (8 годин).
- Немає обмеження кількості спроб входу (rate limiting).
- Один адміністратор без ролей, реєстрації та відновлення пароля — це поза межами завдання.
- Попередження про незбережені зміни спрацьовує при закритті чи перезавантаженні вкладки, але не при переході за посиланням усередині сайту.
- Лічильник символів рахує довжину рядка JavaScript, тому емодзі враховується як 2 символи. Сервер рахує так само, розбіжностей між формою та сервером немає.
- SQLite розрахована на один екземпляр застосунку.
- `better-sqlite3` — нативний модуль. Після зміни версії Node потрібно виконати `npm rebuild better-sqlite3`.
- Для e2e-тестів має бути вільний порт 3100.

## Незавершені частини

Обов'язкова частина завдання виконана. З бонусних завдань зроблено CI (див. розділ [CI](#ci)), Docker Compose — ні: проєкт і так запускається без Docker.

Не виконувались:

- генерація опису та SEO-полів через LLM;
- імпорт товарів із Shopify;
- дизайн у Figma чи аналогічному інструменті.
